## 二、项目介绍

“一箭又一箭”是一个点击式箭头解谜游戏。棋盘中的箭头分别朝上、下、左、右。点击箭头时，程序会检查它前进方向直到棋盘边界的所有格子：如果没有其他箭头，箭头就沿当前方向飞出并消失；如果存在阻挡，箭头会变红、向前轻撞后退回，同时扣除一次失误机会。每关有 3 次失误机会，清除全部箭头后进入下一关，机会耗尽则可以重新挑战。

项目包含 3 个固定关卡、开始与结果界面、剩余箭头和失误次数显示、重新开始功能，以及飞出和碰撞动画。所有图形均由程序绘制，没有使用原商业游戏素材。

## 三、实现思路

每支箭头使用编号、行、列和方向表示，例如 `(a01, 2, 3, right)` 表示编号为 a01、位于第 2 行第 3 列并朝右的箭头。关卡保存棋盘行列数、初始箭头集合和允许失误次数；重新开始时重新复制这份初始数据。

路径检测不需要遍历整个二维数组。程序遍历当前仍存在的箭头，只保留与被点击箭头处于同一行或同一列、并且严格位于其前进方向上的箭头。如果没有这样的箭头，路径畅通；如果有，则距离最近的一支是首次碰到的阻挡物。规则层不依赖 Pygame，因此可以单独进行自动化测试。

关卡使用固定数据。优化时，Codex筛选了第二、三关的箭头方向，增加阻挡依赖；第一关保持教学布局。求解器反复删除当前可飞出的箭头：删除不会增加阻挡，因此无需回溯。如果剩余箭头中没有一支能走，就判定无解。三关均通过验证，但这只能证明可解，新布局仍需要本人实际试玩。

关键判断可概括为：右箭头只检查同行且列号更大的箭头；左箭头检查同行且列号更小的箭头，上下方向同理。找到的箭头中距离最近者就是碰撞对象。

路径检测关键代码（摘自game_core.py）：

```python
row_gap = other.row - arrow.row
col_gap = other.col - arrow.col
same_ray = (
    (dr == 0 and row_gap == 0 and col_gap * dc > 0)
    or (dc == 0 and col_gap == 0 and row_gap * dr > 0)
)
```

其中dr、dc是方向的行列增量。同行/同列排除侧面的箭头；差值与方向增量的乘积大于0表示在前方，因而不会把后面的箭头误判为阻挡。

## 七、心得体会

这次作业中，我主要负责提出需求、选择界面风格、实际试玩并反馈问题，代码实现、自动测试和具体修复主要由Codex完成。AIGC让我较快得到了一款能够运行的小游戏，但实际开发也说明，程序能够启动、测试显示通过，并不意味着玩家操作起来就没有问题。

第一个明显的问题来自试玩：点击一支箭头后，必须等它的飞行动画结束才能点击下一支，游戏节奏因此显得很慢。我把这个现象反馈给Codex后，程序改为允许多个飞行动画同时播放。后来又调整了碰撞反馈：当阻挡物已经被移走时，原箭头可以立即重试。这个过程让我意识到，动画不仅是视觉效果，它与输入处理之间的关系也会直接影响操作体验。

另一个问题出现在全部通关界面，“返回首页”看起来无法点击。我提供截图后，Codex定位到页面其实已经切回首页，但旧关卡的通关状态又把页面切回了结果界面。这让我认识到，排查界面问题不能只看按钮本身，还需要检查点击之后的状态更新。两次反馈都来自实际操作，也说明人工试玩和自动化测试各有作用。

后续优化还调整了关卡的阻挡关系，并补充了通过点击坐标走完三关的测试。相比单纯增加箭头数量，增加需要逐步解除的阻挡更能体现关卡的层次。对于AI给出的实现，我需要关注的不只是“是否生成了代码”，还包括结果是否符合规则、能否正常通关，以及问题修复后有没有影响其他操作。优化完成后，我对当前版本的整体体验比较满意。

过程记录也是这次作业的一项收获。我在开发前就要求保留AIGC使用过程和模块计时，但助手没有完整落实，后来通过原始会话与Git记录重新核对了时间线。这让我看到，委托AI记录过程后，也需要检查它是否按要求执行。真实的报错、试玩反馈、修复提交和可复核的时间，比笼统地写“使用AI完成开发”更能说明协作过程。后续我会继续明确区分自己的工作与AI完成的内容，并结合代码和测试理解关键逻辑。
